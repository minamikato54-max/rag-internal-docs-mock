## 案件の一言まとめ

従業員50名のIT企業の情報システム部長から、「社内の PDF・Word をAIに読ませ、チャットで質問すると答えるシステム。できれば Slack から。社外に情報が漏れるのは絶対NG」という依頼。**中級案件**（2週間で土台＝MVPを作る提案）。

## 中級案件で必ず見る4点（講師）

| 見るところ             | なぜ大事か                                                           |
| ---------------------- | -------------------------------------------------------------------- |
| 文書の量と更新頻度     | 本数で設計と費用が桁違いに変わる。更新が多いと読み直しの仕組みが要る |
| 今ある環境とのつながり | 初日に聞かないと「使えない」になる（Slack・AWS・VPN・ログイン）      |
| 見られる文書の細かさ   | 後から足すと作り直し。部署別かどうか                                 |
| 精度の期待値           | 「AIなら100点」を最初に直す。書かれていないことの判断はさせない      |

## 今回の学び（次の案件にも使う）

### ヒアリングの組み立て

- **答えやすい質問を先に**：困りごと → 検索したい文書 → 使う人 → 予算・時期。技術の細部（ログイン方式・VPN・認証規格）は2回目に回し、担当者に確認する。
- **精度の数字を先に約束しない**：文書や質問の難しさが分かる前に「8割」と言わない。実際によくある質問で試して、一緒に目標を決める。
- **検証用の素材をもらう**：「実際に検索したい質問3〜5個と、答えが載っている文書」。動作確認と精度の検証に使える。
- 良い点として評価された質問：閲覧権限、外部AIへの送信可否、Slackの回答の公開範囲、現状の検索時間・月の回数・よくある質問。

### 提案の組み立て（回答を受けて）

- **全部を2週間でやらない**。MVPに入れるものと、Phase 2に回すものを分ける。
- Phase 2は「やらない」ではなく「次の段階で」と書く（失注を防ぎ、信頼を得る）。
- SOC2のような認証は、MVPで完全準拠はできなくても、「準拠を意識した設計」（国内リージョン・認証・環境変数管理）を示し、Phase 2で目指す道筋を書く。

## 提案書を書く前に確認する点（今回気づいたこと）

| #   | 確認すること                 | 理由                                                                                                                                                 |
| --- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 精度の書き方                 | 「80%以上」を約束せず、テスト質問で検証して目標を決める手順にする                                                                                    |
| 2   | **外部のAIへの送信**         | DBが国内でも、Embedding・回答生成のAPIに文書の内容を送る。「漏れるのは絶対NG」とぶつかる可能性。学習に使われない設定・送信先の国・保存期間を説明する |
| 3   | **MVPでの閲覧制限**          | 部署別の制御はPhase 2。MVPでは全員に見えてよい文書だけ取り込む、と明記する                                                                           |
| 4   | Embeddingの選択              | Claude APIに埋め込み専用があるか未確認。実装前に調べる                                                                                               |
| 5   | 既存環境（AWS・VPN）との違い | 提案はVercel+Supabase。理由と、将来寄せる余地を一言入れる                                                                                            |
| 6   | 仮定の数字                   | 「1人月5時間」などは回答に無い。仮定と書いて「要確認」にする                                                                                         |

## 実際の案件で使うチェックリスト

- [ ] 依頼文のキーワードごとに、確認したいことを書き出した
- [ ] 質問は「答えやすい順」に並べた（技術の細部は後ろ）
- [ ] 精度は数字で約束していない
- [ ] 検証用の質問と文書をもらう依頼を入れた
- [ ] 外部AIへの送信の可否を聞いた（受注に関わる）
- [ ] 閲覧制限（部署・役職）を聞いた
- [ ] 現状の探し方・所要時間・月の回数を聞いた（効果の試算用）
- [ ] MVPとPhase 2を分け、Phase 2の道筋を書いた
- [ ] 「できます」と言い切らず、仮定は「要確認」と書いた
- [ ] 見出しは名詞で短く、本文は箇条書きと表。見てすぐ分かる形にした
